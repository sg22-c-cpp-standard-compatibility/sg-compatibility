## Paper #1 Removing Digraphs - D4235R1

- Has some SG15 feedback but matches the current mailing so far

- Matthias gives a brief runthrough of the timeline
  - C95 added digraphs and C++98 did too
  - Ambiguous with scope resolution
  - Trigraphs were removed from C++ and C
  - It was requested to be removed because it messes with the splicer syntax, causes issues with reflection
    Interpolated string literals also cannot be used with digraphs due to the closing curly brace
    Additionally causes issues with `std::format` so there are a lot of issues that are difficult to resolve.
    They cause issues with numerous encodings too.
  - publicly available digraph usage is typically demo code and compiler test code.
  - Clang and EDG have the ability to disable them already.
  - multiple encodings do not support _Pragma spelling.
  - potentially it may need to only need to be retained for #pragma, or another potential spelling may be required
  - SG16 suggested removing it already

- Jens G - Opposes removal from C on the grounds that there's legitimate usage for Less-Equals and various other symbols. Digraphs are replaced/recoginzed tokenization so in C they are not an issue within strings they're only recognized in the token stream when they are recoginzed as tokens. potential 3-char or 4-char digraphs could be used to prevent issues around new symbols being introduced in C++

- Matthias pointed out a potential confusion within the example because it is in a string as it is an interpolated expression

- Jens G said it's not potentially an issue with C

- Hubert countered and said it can be an issue in the future with potential further C language evolution
  especially considering C has been adopting C++ features and this could cause issues later

- Corentin asked for elaboration on Jens' first point

- Jens said that digraphs are important to him in C and he would like to introduce Unicode characters in the future to represent some digraphs like LEQ NEQ EQ

- Corentin said that the digraph for LEQ and NEQ are not going away.

- Jens is okay with partial removal on the basis that there's a high confidence that certain digraphs are unused

## Paper #2 $identifiers - P4234R2

- Matthias mentioned that this is one of the oldest extensions as it allows pre ANSI C code conformance.
  `$` was added to the basic character set in C++26 and it made the extension non-conformant so this deals with that
  - Very prevalent usage of `$identifiers` in the wild
    all provided C++ compiler examples aside from EDG allow them as default
  - opt-out was removed from some compilers because it caused issues with Apple targets

- Question for WG14 asked if only supporting it would be the conforming option

- Jan said this is an alignment paper SG16 said unconditionally permit the use of $ in identifiers
  mentioned potential issues around name mangling

- Matthias - assemblers have directives to replace incompatible symbols if needed so it should be a non-issue

- SG16 final recommendation is unconditionally allow them

- Jens said it is relatively unproblematic because platforms that don't allow it already cannot compile so it should be fine. Might be an issue with WG14.

- Hubert - reemphasizes for WG14 that WG21 is very allergic to what WG14 chose (Officially acknowledge that it was opt-in and opt-out) as it could introduce complexity around code resolution and could break future compat.

- Jan - said making it conditional can mess with syntax highlighting and that can make stuff difficult to read

- Jan noted that it may also require a WG14 paper

- Aaron mentioned that there's other languages built on top of C/C++ that may have problems with this change
  pointed out HLSL using `$var` as predefined globals, could be an issue but there is a chance.

- Matthias - given how popular it is and is default enabled, these languages probably already have this issue if they are to have it.

- Rajan - Answered to Aaron, mentioned the difference between usage and allowance and how it might not be used despite being allowed.

- Aaron - sides with disabling it by default

- Matthias - downstream are probably aware that this could already cause issues but he has not seen any

- Tom - `$` is just used as identifier in HLSL but not an operator so it should be ok

- Jan asked to go through the other options.

- Matheus - mentioned issues with things like `$1` and potentially banning such a pattern
