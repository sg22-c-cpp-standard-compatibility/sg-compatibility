## P3290R4 Integrating Existing Assertions with Contracts

(Jan Schultke chairing, Giuseppe D'Angelo scribing)

- JB: (Joshua Berne) Presenting D3290R5:
  This paper started when we researched how to integrate the pre-existing macro-based contract/assertions with the standardized C++ Contracts.
  At the end we decided to expose a library interface, so that existing macros can hook with it.
  The other thing is the assert() C macro, and we want also to integrate it. We can modify it so that when the assert fails it calls contract_violation etc. This is opt-in -- behind a macro to enable this feature. Otherwise works the same way, including w.r.t. `NDEBUG`.
  Since `assert()` comes from C, there's an overlap there, incl. the shape of the opt-in. Is a macro OK?
  After discussion on the reflector, we're using a `__STDC__` prefixed macro.
  When it comes to C++ there's also a FTM as expected.
  There's implementations available (links on Mattermost).
  That's all. Questions: is the name of the macro ok? Is this how we want to do this kind of integration?

- VV: (Ville Voutilainen)
  I find the need to terminate (when using contracts) possibly unnecessary, we may want also a non-terminating semantic; e.g. using throwing violation handlers.
  About the macro: I'd like if we can find some "magic" wording so implementations can bypass the macro.
  Also there's the discussion about having in-source decision of the evaluation semantic, something to consider here.

- JB: This is not about making the C `assert()` make everything contracts can do. The idea is just to integrate with the violation handler.

- VV: I disagree with that goal.

- Tom Honermann: About throwing violation handlers: I see `assert()` as a C facility, more than a C++ feature, so I don't find the need of throwing out of it very compelling. People that need that can define their own `assert()`. This doesn't overrule people from defining their own macros, right?

- JB: Right. We never prevented anything of the sorts. Furthermore we're providing entry points.
  The only question is whether the violation handler triggered by C's `assert()` can throw. I don't think everyone has ever expected this to work. I'd be wary to add this feature / make this change.


- Aaron Ballman: This is a decision that happens when you include `assert.h` / `cassert`, right?

- JB: Correct. `assert()` is a macro, depending on what's defined before you include it, it changes (`NDEBUG`). We're extending it so that when it triggers it calls the contract violation handler.

- AB: I have to wrap my mind whether it's a good thing that it's a case-by-case decision what `assert()` does.

- Corentin Jabot: I think the paper is fine as-is. I support it. If we were to change the behavior of C's `assert` I would change my opinion and go against this paper. It should still `abort()` / `terminate`.

- VV: I don't think it's correct to describe `assert()` as a C facility. It's also a C++ facility, used by C++ projects (that don't have C in there). We shouldn't be concerned by the fact that C code using `assert()` can't cope with throwing violation handlers, the same concern exists with C++ code; people using them throwing handlers what they're doing. IOW it doesn't mean the possibility shouldn't be there.

- Jan Schultke: How does this work with modules? If you were to `import std`, how do you say "`assert` should use contracts"?

- JB: you don't get `assert()` when you `import std`.

- AB: If I have some header shared between C/C++ , and you define the `__STDC_WANT_xxx_` macro before including `assert.h`, what is a C user supposed to expect from the code? Is it going to do something there?

- JB: C will need contract support for it to mean something, but this is future-proofing the feature.
  We could have a `STDCPP` macro for now and add a `STDC` later when C gets contracts, but that sounds overengineering (?)

- AB: I don't think C will ever get contract violation handlers in the same shape that C++ has, so a different macro may make sense, but ultimately I don't think this is a blocker

- JB: The goal of this is to unify the violation handling, every library and project has its own contract violation machinery, we also want violation handling from C/C++'s `assert()` to be unified
  A C violation handler will look different (esp. the types involved of the violation object) but most of the machinery can be shared, it's all in the runtime library, shared across the program. This can extend to C code. Have just one violation handler for both C and C++

- VV: I can confirm this (as independent implementator)
  At the same time, we don't necessarily need this unification, one can write a violation handler in one language that calls the handler in the other language.

- CB: Joshua do you remember if we've published the document about the ABI? I think it's useful for people to understand how this is supposed to work

- JB: It hasn't been finished, I intend to still pursue it

- CB: About the name I appreciate that there's a reserved prefix so it won't clash.

- Jan: about polls: one question is about whether you call `std::abort` always or let exceptions propagate

- JB: there's also a question, if a violation handler throws, and you decide not to propagate, do you call `abort()` or `terminate()`

- Jan: another is about the macro. It's a bit strange to see a C macro in the C++ library but nobody seems to strongly have a different opinion.

- JB: maybe just a temperature of the room poll, "are we ok"

- VV: I have a concrete desire that an implementation should be allowed to enable the contract-based `assert()` even without the macro. We need to give the impl. such freedom. The implementation is the same, it's just about the enabling mechanism. (Also allow for throwing violation handlers)

## P3093R0 Attributes on expressions

(Jan Schultke chairing, Timur Doumler scribing)

(Minutes SG22 telecon second half, 2026-07-08 17:25 UTC)

- Giuseppe D'Angelo (GD): presenting P3093R0

- Aaron Ballman (AB): In the original design for attributes, the attribute appertains to things immediately to the left. Why did you choose for it to go to the right instead?

- GD: Because of ambiguities. We can reason about this but the C++ grammar is so complicated that with the "to the left" rule eventually there are clashes. There are some grammar productions where today you can write things like auto ptr = (`new T[123] [[attr]]`) which is legal and `[[attr]]` appertains to the type. So we can't do that here.

- AB: Good to know because I'm currently concerned about it. Our implementation supports Objective-C and I think as proposed this will create ambiguities for Objective-C. But I'm not 100% sure.

- Corentin Jabot (CJ): My concern with this paper is that I don't find the motivation compelling. I don't think there are many valid use cases for attributes on expressions. None of the vendor-specific attributes I know of ever needed to be applied to expressions. This is trying to solve a problem that doesn't exist.

- GD: In some way this is a Catch22. Are concrete attributes on expressions not being proposed because attributes are not allowed to appertain to expressions, or because they don't make sense?

- JS: So you are saying this is a chicken and egg problem?

- GD: Yes.

- AB: Clang has about 500 attributes. None of them are necessary for expressions. We don't have a need for this. None of the non-standard attribute syntaxes (`__attribute__`, `declspec`, etc) support expressions either. We tend to use attributes a lot and we have not found a need for putting them on expressions. So I also am sceptical that there is a motivation here. I agree with the spirit of the original attributes paper [scribe's note: WG21 paper N2761 by Maurer and Wong]. Keywords are almost always going to be a better solution in this space. The lack of prior art makes me question the utility of this proposal.

- Tom Honermann (TH): I share the concern that motivation is not strong. Almost every existing attribute applies to a declaration; the only exceptions I can think of are attributes appertaining to a statement or to a null statement. I can see adding an attribute to an expression alias declaration [scribe's note: that is a proposed new feature] to get this in another way but I don't know how useful even that is.

- Joshua Berne (JB): The lack of anyone having needed this is a red herring. You're not going to start putting attributes on expressions in your own compiler if all other compilers hard-reject them. So the barrier has been high precisely because it's not supported. That's why we haven't seen them so far. I agree that most of the things you want with expressions will have some semantic effect, and that's not what you want to use attributes for, but there are small things where it makes sense: `[[likely]]`, `[[unlikely]]`, `[[nodiscard]]`, that kind of stuff, especially with macros. In C it is actually even more interesting than in C++ because in C++ we will get expression aliases but in C it is unlikely we will ever get that. I think it's a real use case to say "the value of this macro should not be discarded". We may want to use this for focused switching warnings on and off here and there. This does not affect the semantics, and does not seem like a useless thing.

- JS: Doesn't C have some lambda syntax in the works? Where is that proposal at? If you want `[[likely]]`/`[[unlikely]]`, you want that on an expression. Maybe you would want to put a `[[nodiscard]]` on a lambda. It seems this could kinda be accomplished in C if they had some anonymous function kind of thing.

- AB: We have some proposals for something like lambdas, but none of them got consensus so far. So I wouldn't expect anything like that in this decade.

- JB: That would also be a much bigger semantic change.

- JS: I have seen concerns regarding the motivation. We are the compat group. Is there a concern that this C++ syntax would somehow cause problems in C?

- AB: I don't know that this proposal is implementable in a compiler that also supports Objective-C. So I actually do have implementation concerns. Also I am concerned about the amount of memory overhead that this feature would require in the compiler. You'll have a lot more expressions in your code than you have declarations. Maybe we can work around that somehow, so it's not an Over My Dead Body for me, but it seems like a lot of effort for very little win.

- JS: Not sure whether to split the poll up in that case. We really are just working with an encouragement poll. Even if we're primarily about compat, there is still the concern that if everyone in the room feels this is unmotivated, then even if WG21 wants this it won't be in C.

- AB: From a compat perspective we are most worried about things in shared headers which tend to be declarations. So if this hits C++ I am not super worried it will have a massive effect on C.

- JS: But it has been said this can be used in a macro.

- AB: Yeah and both languages have inline macros. So it's not that they can't appear in shared headers, it's just less likely.

- JS: In any case, are we good with the single poll here?

- TD: My comment is not about the poll, but more like a suggestion to the author. Since there were concerns with implementability given the potential clash with Objective-C syntax, may I suggest that the author go and research this aspect before they come back with a revision of this paper?

- GD: Yes, of course, the only reason I haven't done this already is that I haven't even showed this to EWGI, this is the first group I present to, I had no idea if there is any appetite for this, I didn't want to spend implementation effort if it turns out nobody wants this feature.

- Inbal Levi (IL): When we talk about compat with C++, do you also care about preserving semantics in general, like, how much do you care if the user compiles the same code in C and C++ and you get a different meaning for the code?

- AB: Yeah it's a fairly frequent problem. Frequent enough that I wrote a paper about it. Some are more aggravating than others. This doesn't seem aggravating as it doesn't affect declarations.

- JB: Let's take the poll then.
