P4040R1 - Case Ranges
---------------------

Authors: Jan Schultke

- (SCRIBE NOTE: Author is providing paper background and history of the feature, such as being in Clang and GCC for 20 years. C2y recently standardized it.)
- JC: So yeah, this is very helpful for things like parser code and what not. Unfortunately it hurts readability if you can't `switch` and `case` on simple stuff and have to use a `default:` or a fallthrough with the `if` statements. What's different from the existing practice here is the C++-specific stuff, such as scoped enumerations and similar. This is a bit tricky because it uses the underlying type of the enumeration to do the case range, so it enumerates values which may not be possible values. Clang diagnoses mixed enumeration types, but just as a warning. There are some other strategies for handling the mixing of enumeration types, both unscoped and scoped/strong enumerations, such as deprecating them and what not.
- JC: There is pattern matching, but I don't think pattern matching completely occludes the ability to write things this way.
- JC: I'm gonna skip over the template stuff, it doesn't matter for this group.
- TD: So I'm gonna ask a couple questions, and then we can go through the hands. First, we have an example of "0 ... -1", what is going on there?
- JS: Ah, yeah. So that's a peculiarity with `...` and `-` and whatnot, it's actually processed as a single `pp-number`. You need to make sure there's a space there.
- TD: So that's interesting, thank you! But not my question. I was wondering what the value of that range was, what does it do?
- JS: Oh, that's an empty range.
- TD: Okay. So my second question is about the scoped enumerations, if you put that in there it just does the numeric values and not go specifically over the scoped enumeration's member?
- JS: Yes, that's correct. It's over the numeric values.
- TD: Okay. Jens? Gustedt.
- JG: I am wondering if the behavior needs to change here for C++ because of the values of the enumeration might not promote or work exactly like their integer types?
- JS: ... Nooo, I don't think that's how it works?
- (SCRIBE NOTE: discussion around whether or not C and C++ uses this nicely.)
- TD: Okay; just punch that sample code into Godbolt and let it run, should be easy to figure out offline. Jens Maurer?
- JM: I do not think this should work with enum class -- I would want to hear from compiler implementors, moreso in Evolution, about range comparisons and how it works in code today. This is a violation and was introduced more recently than normal enumerations. I am opposed to that, and I think Evolution should consider it.
- JC: I think Jens Maurer said most of what I was going to say. I'm not opposed to this syntax in C++, but I do think that we should not blindly follow the implementation behavior in this space around `enum class` specifically. It probably doesn't need to be discussed in this room and probably in WG21/Evolution, but we need to actually evaluate this in terms of how C++ works.
- AB: So I can speak to implementations insofar as Clang. All we do is check if the thing can be turned into an integer constant value, we do: we did not put much thought into it, we just sort of did it because no real thought was put into it.
- TD: So it sounds like we want to have EWG review this more closely.
- JM: I just want to make clear I am okay with case ranges the feature, standardizing existing practice, all of that. I am SPECIFICALLY talking that EWG review the enum class case.
- TD: Okay. Jan, how do you want to poll this?
- JS: We can give a poll about how concerned we are for `enum class`, since there's no `enum class` or scoped enumerations in C. So it feels almost out of scope for this group, so we should just sort of poll whether or not we want to forward the part that's aligned with C and go from there.
- TD: Yeah, that sounds good enough. Give me a minute to formulate a poll around the paper without the enum class stuff since that seems more like a C++-specific aspect...
- (SCRIBE NOTE: vigorous discussion around integer promotion rules and the like how the poll should look. Lots of discussion comes to the conclusion that the constant values going into switches in both C and C++ both ban value-changing conversions and are handled under the normal rules of `constexpr`, integral promotions, and constant expressions in C++. The behaviors between both compilers end up being identical, and so the point is mostly moot at the end outside of the `enum class` concerns.)


POLL: SG22 supports the addition of P4040R1 "Case ranges" into the C++29 working draft, noting that the C++ specific aspects of the proposed functionality such as enum class and constexpr are out of scope for SG22 review.
